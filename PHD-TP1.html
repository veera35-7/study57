01 · Overview

What this research is — and what it is not

This page replaces the earlier, broader security-threat-detection programme with a single, tightly scoped doctoral topic. Every component below — research questions, papers, datasets, methodology, timeline and references — supports phishing URL detection only.

Parent topic (used consistently across this page):
“An Explainable and Lightweight Machine Learning Framework for Phishing URL Detection in Cybersecurity.”

Problem

Phishing remains one of the most common initial access vectors, and the URL is the cheapest observable signal available before any page is loaded. Detection models must therefore be accurate, fast enough for real-time use, small enough to deploy in constrained environments, and transparent enough to justify a block decision to a human analyst.

Approach

Extract lexical and structural features directly from the URL string, compare traditional lightweight classifiers, reduce the feature set to the minimum that preserves performance, and attach SHAP-based (and, where appropriate, LIME-based) explanations to individual predictions.

Deliverable

A reproducible, lightweight prototype that accepts a URL, returns a phishing/legitimate prediction with a calibrated confidence, and explains the contributing features — supported by evidence of cross-dataset generalization and computational efficiency.

02 · Research Scope

In scope and explicitly out of scope

The proposed framework classifies URLs as phishing or legitimate using lightweight, explainable machine learning. The boundary below is deliberate: it keeps the thesis achievable within the planned period.

In scope

  • ✓Binary classification of URLs as phishing or legitimate.
  • ✓Extraction of lexical and structural URL features (length, token counts, special characters, subdomain depth, TLD, presence of IP address, HTTPS usage, suspicious tokens, entropy, and similar).
  • ✓Feature reduction to lower computational cost without sacrificing detection quality.
  • ✓Comparative evaluation of traditional machine learning algorithms as baselines.
  • ✓Explanation of model decisions using SHAP and, where appropriate, LIME.
  • ✓Reporting of accuracy, precision, recall, F1-score, false-positive rate, model size, training time and prediction latency.
  • ✓Generalization assessment on a separate, independent dataset where feasible.
  • ✓A practical lightweight prototype that accepts a URL and explains its predicted result.

Out of scope

  • ✕General network intrusion detection or anomaly-based traffic analysis.
  • ✕Malware, ransomware or binary analysis of any kind.
  • ✕IoT, SCADA or industrial control system security.
  • ✕Broad coverage of “every cybersecurity threat”.
  • ✕Online learning, concept-drift detection or adaptive learning as mandatory thesis components — these belong to the earlier, broader direction and would expand the project unnecessarily.
  • ✕Full web-page content analysis, DOM inspection or browser-extension engineering.
  • ✕Claims of robustness that are not backed by recorded experimental evidence.

05 · Dataset Strategy

One primary dataset, one independent evaluation dataset

A manageable primary dataset will be paired with an independent evaluation dataset, selected only after checking availability, licensing, labels, feature compatibility and data provenance.

Important distinction — pre-engineered vs. raw URL data. A pre-engineered phishing website dataset (for example the UCI Phishing Websites dataset) supplies already-computed attributes such as SSLfinal_State or URL_of_Anchor, many of which require page or certificate inspection. A raw-URL dataset supplies only the URL string, from which lexical and structural features must be extracted. Their feature spaces are not interchangeable, and mixing them without an explicit mapping would create leakage and invalid comparisons. The thesis will state clearly which type each dataset belongs to and how features are harmonized.
Ethical handling: live malicious URLs will not be collected or visited unnecessarily. Where phishing feeds are used, access conditions and licensing will be respected, and URL strings will be handled in a defanged form wherever feasible.

06 · Methodology

Proposed framework workflow

A single, linear and reproducible pipeline. Each stage produces versioned artefacts that the next stage consumes.

1
Dataset acquisition

Primary dataset plus an independent evaluation dataset, with licensing and provenance recorded.

2
Cleaning & deduplication

Normalization, duplicate and near-duplicate detection, malformed URL removal, label audit.

3
Train / validation / test split

Stratified splits, fixed random seeds, held-out test set untouched until final evaluation.

4
URL feature extraction

Lexical and structural features computed from the URL string only — no page fetching.

5
Baseline ML models

Logistic Regression, Decision Tree, Random Forest and a gradient-boosting model.

6
Feature selection

Filter, wrapper and embedded methods compared; selection performed inside the training fold only.

7
Lightweight model selection

Best performance-to-cost trade-off by model size, training time, latency and memory use.

8
SHAP / LIME explanations

Global feature attribution plus per-prediction explanations, with consistency checks.

9
Independent evaluation

Cross-dataset testing on compatible data; performance drop reported honestly.

10
Prototype

URL in → prediction, confidence and explanation out. Reproducible and documented.

Validity safeguards

  • Leakage prevention: feature selection and hyper-parameter tuning are fitted on training folds only, never on validation or test data.
  • Stratified splits where appropriate, to preserve class proportions across folds.
  • Duplicate and near-duplicate checks before splitting — duplicates split across train and test inflate scores.
  • Class-imbalance handling where needed (class weights, resampling), applied within folds only.
  • Reproducibility: fixed seeds, versioned datasets, versioned experiment configs, logged environments.
  • Leakage-aware design informed by published data-mining and security-ML methodology guidance.

Evaluation metrics

Predictive performance

  • Accuracy
  • Precision
  • Recall
  • F1-score
  • PR-AUC
  • ROC-AUC
  • False-positive rate

Efficiency & interpretability

  • Number of selected features
  • Model size on disk
  • Inference latency per URL
  • Training time
  • Memory use
  • Explanation consistency and usefulness

07 · Research Gap & Novelty

What already exists, and where a defensible gap may lie

Explainable phishing detection and SHAP-based feature analysis are not new. Similar work already exists. A defensible gap can only be identified after a systematic literature review — the directions below are candidates to investigate, not claims.

Existing literature to investigate

  • Traditional machine-learning phishing URL detection and classical URL feature engineering.
  • Feature selection and dimensionality reduction for phishing detection.
  • SHAP and LIME explanations applied to security classifiers.
  • Lightweight and computationally efficient classifiers for constrained or real-time deployment.
  • Cross-dataset generalization and evaluation methodology in security machine learning.
  • Website-level (pre-engineered) versus URL-level (raw-string) detection approaches.

Candidate contribution areas

  • The trade-off between explanation quality and computational efficiency — most studies optimise one and report the other incidentally.
  • Feature stability across datasets — whether the features a model relies on remain influential when the data source changes.
  • Generalization with a compact feature set — how much cross-dataset performance survives aggressive feature reduction.
  • Measurable, reproducible efficiency reporting — model size, latency and memory alongside accuracy, not instead of it.
  • Honest negative results — documenting where the framework does not generalize.
Claim discipline. This page does not claim that explainable phishing detection, SHAP-based attribution or lightweight classifiers are novel in themselves. The novelty claim will be written only after the systematic literature review, and only for what the experiments actually demonstrate.
